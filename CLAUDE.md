```bash
npm run dev              # vite dev server (http://localhost:5173)
npm run build             # production build (adapter-node) into build/
npm run start              # run the production build: node --env-file=.env build
```

There is no lint script/ESLint config — `check` (svelte-check) and `format:check` (Prettier) are the only static gates. Style: tabs, single quotes, no trailing commas, 100-col width (`.prettierrc`).

`npm run start` (and Vite's own env loading) expect a `.env` file — copy `.env.example` and fill in at least `DRAGONITE_URL` (the app's `load` function 503s without it). Most other integrations (`LOCAL_DATABASE_URL`, `KOJI_URL`, `GOLBAT_DATABASE_URL`, Discord OAuth vars) are individually optional — each feature degrades or disables itself when its var is unset rather than crashing the app. `vite.config.ts` loads `.env` itself (via `dotenv`) so `vitest` picks up the same values as `dev`/`build`.

## Architecture

This is a from-scratch rewrite of an older app that used a runtime plugin registry. That approach was deliberately abandoned: **every feature here is a normal, statically-imported part of the codebase** — no dynamic plugin discovery, no registry, no `import()`-by-name. Adding a feature means adding `src/lib/features/<name>/` and wiring its explicit imports into a route — visible in a diff, checked by `svelte-check`.

### Feature-folder layout

```
src/lib/features/<name>/
  types.ts              # domain types for this feature
  server/                # DB access, external API clients — imported only by +page.server.ts / +server.ts
  stores/*.svelte.ts      # client-side Svelte 5 rune stores (only where cross-component shared state is unavoidable)
  components/             # Svelte components
```

Current features: `auth` (Discord OAuth + sessions), `area-management` (Dragonite client, area/worker CRUD, list-filter criteria, Kōji route gen, batch mode), `map` (Leaflet rendering + geofence editor, admin tile-server config), `voting` (token-budget allocation, primary area, weighted tiers, per-area vote targets), `area-requests` (user-submitted add/remove requests + admin review — approving an addition can also set a vote target, enable autoscale, sync the geofence to Kōji, and/or generate a bootstrap route in the same action; members can request an addition as temporary with start/end dates, which an admin manages on the Temporary tab and can only approve via Create area; admins can edit a request's geofence on the review map), `spawnpoints` (Golbat read-only counts + caching), `subscriptions` (optional Discord-role-based lapse check — no external database), `autoscale` (optional per-area Pokémon-worker throttling driven by % of vote target funded — see **Worker autoscale** below), `admin-dashboard` (`/admin/dashboard`'s at-a-glance stats — see **Admin dashboard** below).

### Everything is a SvelteKit form action

There's no separate REST/JSON API layer for mutations (except `/api/koji` and `/api/spawnpoints`, see below). Every write — toggling an area field, voting, saving a geofence, submitting a request — is a named action in the relevant `+page.server.ts` (the home page's `src/routes/+page.server.ts` alone has 13: `toggleField`, `saveWorkers`, `enableAutoscale`, `disableAutoscale`, `allocateTokens`, `setPrimary`, `setAreaTarget`, `saveGeofence`, `saveRoute`, `restoreGeofence`, `deleteGeofenceArchive`, `submitRequest`, `deleteRequest`). Each action re-checks permissions independently (`locals.user?.isAdmin`, etc.) — never assume a check earlier in the request implies later steps are authorized.

`routes/admin/requests/+page.server.ts` has its own five: `resolveRequest`, `createArea`, `setTemporaryDates`, `clearTemporary` and `updateRequestGeofence`. `resolveRequest` refuses to approve a temporary addition (it must go through `createArea`, which writes the `temporary_areas` row and also accepts the optional bootstrap-route checkbox). Approving a removal also deletes any `temporary_areas` row for that area (best-effort). `setTemporaryDates`/`clearTemporary` back the Temporary tab (edit dates, or make an area permanent), and `updateRequestGeofence` saves an admin's edited geofence for a pending request. The area-requests feature folder also holds `dates.ts` and `temporaryView.ts` (pure date rules and tab view-model) plus `server/temporary.ts` and `server/timezone.ts` (storage/scheduler pass and `TEMP_AREA_TIMEZONE` handling). `createArea`'s form bundles a vote-target checkbox, an autoscale checkbox, and a Kōji-geofence checkbox — each optional — into the same submit that creates the Dragonite area (which itself gets quest hours from the `DEFAULT_QUEST_HOURS` env var via `parseQuestHours`, default `[1, 10]` — hours of the day when Dragonite checks for quest changes, not a start/end window), rather than making the admin trigger separate actions afterward. Once the Dragonite area create itself succeeds, the vote-target write, the autoscale enable, and the Kōji geofence save are each independently try/caught and log-and-continue on failure (matching `approveAsCreated`'s own handling just above them) — the area and the resolved request row are already committed at that point, so none of those three failing should look like the whole action failed.

`app.html` has no hard-coded favicon link — it carries a `%zygarde.head%` placeholder that `hooks.server.ts`'s `transformPageChunk` fills from `lib/server/pageHead.ts` (the bundled or `FAVICON_PATH` favicon link, plus the gtag.js snippet when `GA_MEASUREMENT_ID` is set). Both are runtime env so a Docker image is customised without a rebuild; `/favicon` (`routes/favicon/+server.ts`) serves the custom file.

Client code that needs to call an action outside a plain `<form>` (e.g. a button inside a Leaflet popup, which lives outside the Svelte component tree) uses `src/lib/utils/postForm.ts`, which POSTs with `x-sveltekit-action: true` and deserializes the result the same way SvelteKit's own `use:enhance` would.

`/api/koji` and `/api/spawnpoints` are the two real HTTP endpoints, not actions, because they're consumed differently: Kōji generation streams progress via SSE (`ReadableStream` + `text/event-stream`), and spawnpoints are polled from a client store independent of page navigation.

### Permission model

Permissions are resolved **once**, at login (`/auth/discord/callback`) and again at every page `load`, never re-derived deep in a component. The pipeline: Discord guild roles (`SessionUser.guildRoles: Record<guildId, roleId[]>`, one entry per `DISCORD_GUILD_IDS` server the user is a member of, even with no roles) → `hasAccess(roleSetting, guildRoles)` (`src/lib/utils/access.ts`) against one of the role-list env vars (`OFFLINE_AREA_ACCESS`, `ROUTE_ACCESS`, `SPAWNPOINT_ACCESS`). A role list is comma-separated role IDs with **no server key** — Discord role IDs are globally unique — and a server's own ID matches every member of that server (its @everyone role). `parseRoleIds` still accepts the legacy `{"guildId": ["roleId", ...]}` JSON by flattening it, so old `.env` files keep working; keep that compatibility. `ROUTE_ACCESS` covers all three route layers, with the legacy `POKEMON_/FORT_/QUEST_ROUTE_ACCESS` still granting their own layer. `isAdmin` comes from `ADMIN_DISCORD_IDS` instead of a role. Voting tier resolution (`src/lib/features/voting/server/tiers.ts`) uses each tier's own `roles` in `VOTE_TIERS` (falling back to the legacy `VOTE_TIER_ROLES` per tier) and adds a weight and an admin-override table (`user_tier_overrides`) that takes precedence over role-derived tier. The OAuth redirect URI and resolution-DM links are derived from the request origin (`ORIGIN` in production); `DISCORD_REDIRECT_URI` is only an optional override, and `SITE_URL` no longer exists.

`hooks.server.ts` hydrates `locals.user` from the session cookie on every request and hard-gates the whole `/admin` path (403 if not `isAdmin`) before any route code runs; `routes/admin/+layout.server.ts` re-checks the same thing (defense in depth, not redundant with hooks — each admin route's own `load`/actions also check independently, matching the "every action re-checks" rule above).

A user whose roles (or subscription — see below) don't resolve to any configured tier gets `NO_ACCESS_TIER` (`voting/server/tiers.ts`, weight 0) — **not** the lowest-weight tier in `VOTE_TIERS`. A tier with no `roles` (and no legacy `VOTE_TIER_ROLES` entry) matches nobody. Don't assume an unmatched user quietly falls back to some non-zero tier. The one exception: with `VOTE_TIERS` unset entirely, `parseVoteTiers` returns `[DEFAULT_TIER]` and `resolveTierFromRoles` gives everyone that tier (weight 1), recognised by object identity — so a fresh install can vote. Malformed `VOTE_TIERS` JSON gives no tiers at all (everyone 0, error logged), never the default, so a typo can't hand out tokens.

### Voting: tokens, targets, and budget enforcement

A resolved tier's weight (above) doubles as a spendable **token budget**. `voting/server/votes.ts`'s `allocateTokens` lets a user spend it across areas (`area_votes.amount`), replacing an earlier unlimited weighted-toggle model; `getUserTokenBudget`/`getUserAllocatedTotal` are the only source of truth for spent-vs-available. Whenever a user's weight is _written_ — Discord login resolution, an admin tier override (`upsertUserTier`/`applyResolvedTier`), or subscription sync — that write path must also call `enforceUserBudget`, which trims existing allocations down to the new (possibly lower) budget oldest-first, preserving the primary area's allocation first. `allocateTokens` itself only guards against _exceeding_ budget on the way up; it never re-checks existing rows, so a new weight-writing code path that skips `enforceUserBudget` is a real bug, not an edge case — grep for its three existing call sites before adding a fourth.

`voting/server/targets.ts` (`resolveTarget`) is a separate, purely-derived concept: an admin-configured per-area token target (a static number, or `ceil(pokemonWorkers / workersPerToken)`, with a per-area override of the global ratio from `voting/server/settings.ts`), used to render funded/target progress on area cards (`VoteTargetForm.svelte`, admin-only) and to drive worker autoscale (below). It never gates `allocateTokens` — an area can run over- or under-target freely.

**Every caller of `resolveTarget` in `workers` mode must pass `autoscale/server/state.ts`'s stored `max_pokemon_workers`, never the area's live `pokemon_mode.workers`.** This isn't a style preference — it prevents a real feedback loop: if autoscale is throttling an area's workers down and the target were computed from that same live (already-shrunk) count, the target would shrink right along with it, making the area look _more_ funded and immediately scaling it back up, forever. `autoscale/server/state.ts`'s `ensureAutoscaleRows` backfills a `max_pokemon_workers` baseline for every area (disabled, snapshotting the current count) the moment it's first seen — regardless of whether autoscale is ever turned on for it — specifically so this stable number always exists for `resolveTarget` to use.

### Worker autoscale

`autoscale/` throttles an area's Pokémon worker count to a percentage of a fixed baseline based on how funded its vote target currently is — entirely optional and opt-in per area (`area_worker_autoscale.enabled`).

- **The baseline (`max_pokemon_workers`)** is snapshotted from the area's _live_ Dragonite worker count at the moment autoscale is enabled (or re-enabled) — never computed or inferred. Disabling restores the area to this exact number and leaves it stored, so re-enabling later doesn't need to re-derive anything; only an explicit enable/re-enable ever changes it (see the feedback-loop note above for why nothing else may).
- **Tiers** (`autoscale/tiers.ts`, pure — shared by both server and the admin UI, like `map/geometry.ts`): 100% funded → 100% speed, 60–99% → 75%, 30–59% → 50%, 1–29% → 25%, 0% → 10%. `computeScaledWorkers` rounds to the nearest worker, floored at 1 — even the bottom tier keeps an area alive rather than starving it to 0.
- **Enabling requires a vote target already be configured** (`enableAutoscale` action fails otherwise) — without one there's nothing to compute a percentage against, and the area would silently sit at the lowest tier with no visible reason why.
- **`autoscale/server/sync.ts`'s `runAutoscaleSync`** is the one place that ties it all together: resolves each enabled area's target (off the stored max, per above), computes % funded and a tier, and `patchArea`s Dragonite only when the tier calls for a different worker count than it currently has. It's invoked from three places that all share this same function: the scheduler (below), the admin "Run Autoscale Sync Now" button (`/admin/autoscale`, for not waiting out the current interval), and nowhere else — mass enable/disable (`BatchPanel.svelte`'s Autoscale batch action) only flips `enabled`/restores the baseline per area, one `postForm` call per area, same as the single-area actions; it does not itself trigger a sync pass.

### Admin dashboard

`/admin/dashboard` is read-only and assembled in its `load` from pure functions in `admin-dashboard/server/`: `computeStats.ts` (token-goal buckets, enabled/throttled counts, workers, tokens), and `voteReport.ts`'s `computeVoteReport` (areas with/without votes, voter counts, top voters) and `computeAreaRanking` (one row per voted area: all vs. subscriber tokens and voters, resolved target, baseline workers). The ranking's target follows the usual rule (stored autoscale max, see Voting); its `baselineWorkers` matches `computeStats`' — the autoscale max only where autoscale is _enabled_, else the live count, because the stored max is a stale snapshot for areas autoscale isn't managing. Sorting (all vs. subscriber tokens), Top 5/10/All and % of goal are client-side in `admin-dashboard/ranking.ts` (pure, tested). Every admin page gets its nav bar and "back to areas" link from `routes/admin/+layout.svelte`; don't add per-page back links.

**Admin UI kit.** All `/admin` pages share one look: wrap the page in `$lib/components/admin/AdminPage.svelte` (title, meta line, success/error `banner` from the form action) and group content in `Panel.svelte` cards (optional `title`, `hint`, and an `actions` snippet for header controls). Controls use the shared classes defined in `routes/admin/+layout.svelte` — `.btn` (+ `-primary`/`-success`/`-danger`/`-sm`), `.field`/`.field-label`/`.input`/`.check`, `.segmented` (`aria-pressed` buttons or `aria-current` links), `.badge` (+ `-good`/`-warn`/`-danger`/`-accent`/`-violet`), `.count`, `.data-table` in a `.table-wrap`, `.hint`, `.empty`, `.card-label`. They're `:global` but scoped under the layout's `.admin-shell`, so they work in feature components rendered on admin pages (e.g. `CreateAreaForm.svelte`) and can never leak into the main app. Don't re-declare these per page; a page-scoped rule that must override one (e.g. hiding a `.segmented`) needs higher specificity than the shared two-class selector. `voteReport.ts` owns its own query (`getDashboardVoteRows`, one row per non-zero `area_votes` allocation joined to `user_tiers`, `user_tier_overrides`, and `subscription_role_checks`) and ignores votes on area ids Dragonite no longer returns, so lingering rows for deleted areas never show up in a count or list. "Active subscriber" (`isActiveSubscriber`) means a role-resolved tier (weight > 0, not an admin override) with no current failing subscription-check streak — derived purely from stored state, never a live Discord lookup, so loading the dashboard can't burn Discord rate limit. Top voters are computed server-side at `TOP_LIMIT` (10); the Top 5 toggle only slices client-side.

### The `QueryExecutor` pattern

Server modules that touch the local DB (`votes.ts`, `requests.ts`, `tiers.ts`... one per feature) never import the DB pool directly. Instead they declare their own minimal `QueryExecutor` interface (usually just `execute(sql, params)`) and take it as a function parameter. Callers pass `getPool(env.LOCAL_DATABASE_URL)` (cast to that interface — `mysql2`'s real overloads don't structurally match but are runtime-compatible). This is what makes the whole `server/` layer unit-testable without a real MySQL connection: tests just pass `{ execute: vi.fn() }`. Follow this pattern for any new DB-backed module rather than importing `getPool` inside it.

The local DB's whole schema lives in one place, `src/lib/server/db.ts` (`SCHEMA_STATEMENTS`, run via `ensureSchema()` from `hooks.server.ts` at boot) — one `CREATE TABLE IF NOT EXISTS` per feature, plus `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` for later-added columns on existing tables. Add new tables/columns there, not in migration files.

### Map/Leaflet state

Leaflet owns its own DOM and isn't reactive, so the two client stores that wrap it (`mapState.svelte.ts`, `editState.svelte.ts`) deliberately mix `$state` reactive fields (selection, visibility toggles) with plain non-reactive fields (the `L.Map`, layer groups, `Map<areaId, Polygon>`) — don't try to make the Leaflet objects themselves reactive. `editState` never imports `mapState`; whichever component drives an edit passes the Leaflet primitives in as parameters, keeping the two stores independently testable/reasoned-about. The vertex/midpoint/snap editing core is `map/vertexEditor.ts` (`VertexEditor`), shared by `editState` (main map) and `RequestMapPreview` (admin request review); its handle styles live in `map/editHandles.css`. Geofence data crosses the Dragonite boundary as GeoJSON (`[lon, lat]` per RFC 7946) and is converted to/from the editor's internal `[lat, lng]` vertex arrays in `src/lib/features/map/geometry.ts` — that's the one place the axis flip happens.

**Call `layer.openPopup()` before `mapState.focusArea()`, never after.** Opening a popup triggers Leaflet's own `autoPan`, which — if it runs _after_ `focusArea`'s `fitBounds` — nudges the just-centered view again to bring the popup fully into frame, leaving the area off-center at the viewport edge instead of centered. `AreaList.svelte`'s `selectFromList` and `mapState.onMobileMapActivated` (which also fires on every list selection, desktop included, via `MapPanel.svelte`'s effect on `mobileView`) both open the popup first for this reason. Clicking a polygon directly on the map doesn't have this problem, since Leaflet's own click-to-open-popup handler (registered by `bindPopup`) already fires before our separate `focusArea`-calling click handler.

**`/?area=<id>` deep link** (`area-management/deepLink.ts`, handled once in `AreaList.svelte` after `mapState.mapReady`): selects and expands that area the same way a list click does, then calls `mapState.onMobileMapActivated` directly for the popup-then-focus ordering above (not via a `mobileView` change — `mobileView` persists across visits, so it may already be `'map'` and nothing would fire), then strips the param with `replaceState`. This depends on `MapPanel`'s teardown resetting `mapState.mapReady`/`map`: `mapState` is a singleton that outlives the page, and a stale `mapReady = true` after client-side navigation would let anything waiting on it act on the removed map. It also depends on `initMap`'s initial fit-all being **non-animated**: Leaflet silently drops a zoom requested while another zoom animation is still running (`_tryAnimatedZoom` bails while `_animatingZoom`), so any programmatic `fitBounds` shortly after the map loads would otherwise vanish. Link to areas from elsewhere with `areaLink(id)` rather than hand-building the URL.

### External integrations

Each external service gets exactly one client module under the feature that owns it, all called only from server-side code (`+page.server.ts`/`+server.ts`), never from the browser:

- `area-management/server/dragonite.ts` — Dragonite v2 area CRUD (`/v2/areas/`). Note the API is paginated (`page`/`per_page`, `X-Total-Pages` header) and geofences arrive as GeoJSON `Feature`/`Polygon`/`MultiPolygon`.
- `area-management/server/koji.ts` — two different call shapes for two different Kōji capabilities. The route-generation helpers (`buildKojiRequest`, `extractRouteCoords`, etc.) are pure request/response shaping with no fetch of their own; the actual HTTP call lives in `area-management/server/kojiHttp.ts` (`kojiPost`, shared by `routes/api/koji/+server.ts` and `bootstrapRoute.ts`; the latter is what `createArea` on the requests page uses to save a bootstrap route to a new area, with a 120 s overall timeout) using raw `node:http`/`https` (not `fetch`) specifically to set TCP keepalive, since long-running Kōji computations get silently dropped by NAT/firewalls otherwise. Generated routes are cached to `route-backups/<key>.txt` on disk before the `saveRoute` action writes them to Dragonite (crash recovery) — in Docker this directory needs a volume mount (`docker-compose.yml.example` already declares one) or backup files are lost on container restart. `saveGeofence`, by contrast, _does_ call `fetch` itself — it's a single quick write (`POST /api/v1/geofence/save-koji`), not a long-running computation, so it doesn't need the keepalive treatment. It upserts **by name**: Kōji looks up an existing geofence by the submitted name and overwrites it in place if found, with no conflict error — and "overwrite" means rebuilding the row from the payload alone: `parent` nulled unless `__parent` is sent, `mode` reset to `unset` unless `__mode` is sent, every custom property deleted (only `projects` survives, since they're rewritten only when `__projects` is sent). A nulled parent is what drops fences out of Poracle's grouping. So `saveGeofence` is **only for creating** a geofence: `createArea` calls `kojiGeofenceSync.ts`'s `checkKojiGeofenceName` first and refuses (before creating the Dragonite area) if the name is already taken, case-insensitively.
- `area-management/server/kojiGeofenceSync.ts` — **updating** an existing Kōji geofence's shape, for the "Also update in Kōji" option on `saveGeofence`/`restoreGeofence` (map editor, raw GeoJSON, history restore; off by default, gated on `permissions.canSyncKoji` = admin + `KOJI_URL`). It uses Kōji's _admin_ API rather than `save-koji`: `POST /config/login` (password = `KOJI_SECRET`, returns an `id` session cookie — the admin API ignores the Bearer header), `GET /internal/admin/geofence/{name}/` to read the row, then `PATCH /internal/admin/geofence/{id}/` with only `name`/`geometry`/`parent`/`mode` (parent and mode echoed back unchanged). Kōji's `geofence::Query::upsert` only rewrites projects/properties when those keys are present, so omitting them is what preserves them — never add `projects` or `properties` to that PATCH body. Kōji's name lookup is case-insensitive and treats an all-digit name as an id, so `syncGeofenceToKoji` requires the returned `name` to match exactly and otherwise skips; it never creates a geofence and never throws (returns `synced`/`skipped`/`failed`, which the action passes back as `koji` for the client to `alert` via `kojiSyncNotice`). It runs only after the Dragonite patch succeeds, so a Kōji problem never fails the save. A missing geofence comes back from Kōji as a 500 with `Does not exist` in the body, not a 404.
- `spawnpoints/server/golbat.ts` — direct read-only MySQL queries against Golbat's own DB (`GOLBAT_DATABASE_URL`, a separate connection from `LOCAL_DATABASE_URL`), with results cached in the local DB (`spawnpoint_cache` table) since Golbat can be slow to query.
- `auth/server/discord.ts`, `area-requests/server/discord.ts`, and `voting/server/discord.ts` — Discord REST calls (guild role lookups, alert embeds, resolution DMs), using `DISCORD_BOT_TOKEN`. `auth/server/discord.ts`'s `fetchGuildRoles` (a per-member `GET /guilds/{id}/members/{id}` lookup, deliberately not a bulk member list — that needs Discord's privileged Guild Members intent and triggers bot verification) is shared by both login and `subscriptions/server/discordRoleCheck.ts` below; it retries on a 429 honoring `Retry-After` rather than misreading a rate limit as "user has no roles."
- `lib/server/alerts.ts` — the one Discord webhook all alerts share (`DISCORD_ALERT_WEBHOOK_URL`), gated per event by its own `ALERT_*` true/false toggle (`ALERT_TOGGLES`). Features build their own embeds and call `postAlert(event, embeds)` — never read a webhook URL from `env` directly; a new alert type is a new `ALERT_TOGGLES` entry, not a new webhook env var.
- `subscriptions/server/discordRoleCheck.ts` — no database or connection of its own; checks one user's current roles in the `DISCORD_GUILD_IDS` servers via `fetchGuildRoles` above plus `hasAnyRole` (same utility permission checks use), against the `SUBSCRIPTION_REQUIRED_ROLES` role list. Its candidates are every user with weight > 0 and no override, so it doesn't mix with a free tier: free users would be downgraded too (the README warns about this).

All five follow the same "unavailable, not broken" convention: an unset URL/config makes the feature disable itself (empty state, a disabled button, a 503 only on the specific action that needed it) rather than failing app-wide.

### Background jobs (`src/lib/server/scheduler.ts`)

The one exception to "every mutation is a form action, triggered by a request": four jobs run on their own timers, all started once from `hooks.server.ts` (`startSubscriptionSyncScheduler` / `startWorkerAutoscaleScheduler` / `startOrphanVoteCleanupScheduler` / `startTemporaryAreaScheduler`, each behind its own `started` flag guarding against double-start) and all log-and-swallow errors so a job failure can never take down the app.

**Subscription sync** reuses `db.ts`'s ordinary local `getPool()` — no separate database connection, since the check itself is a Discord REST lookup (`discordRoleCheck.ts` above), not a query against an external DB. Each run walks every currently-elevated, non-overridden user (`voting/server/votes.ts`'s `listUserTiers`), paced ~250ms apart to stay well under Discord's rate limits for a whole-community daily check. `subscription_role_checks.failing_since` marks the _start_ of a user's failing streak — set once on first failure, left untouched on repeat failures, cleared on any pass — not "the last time a check failed"; overwriting it on every failure would perpetually reset the grace-period clock (configured from `/admin/tiers`) and no one would ever lapse. Uses a plain `setInterval` — runs once immediately, then every fixed 24h.

**Worker autoscale sync** (`runAutoscaleSync`, see **Worker autoscale** above) is _self-rescheduling_ with `setTimeout` rather than `setInterval`, specifically so `voting_settings.autoscale_interval_minutes` (admin-configurable, `/admin/autoscale`) can change without an app restart: each run reads the current setting only when scheduling its _own next_ run. This has one gotcha worth knowing — lowering the interval doesn't preempt a wait already in progress, since that wait was scheduled using whatever the setting was at the time; it only takes effect starting from the tick after the one currently pending. The admin "Run Autoscale Sync Now" button on `/admin/autoscale` exists specifically to sidestep this without waiting out the old interval.

**Temporary areas** (`area-requests/server/temporary.ts`'s `runTemporaryAreaPass`, wired in `scheduler.ts`) is a plain hourly `setInterval` (runs once at boot too; needs `LOCAL_DATABASE_URL` and `DRAGONITE_URL`). Each run computes `today` in `TEMP_AREA_TIMEZONE` (`tempAreaToday`), then per `temporary_areas` row: enables the area the day before `starts_on` (stamps `started_at`), DMs the requester the day before `expires_on` (`notified_at`, stamped even if the DM fails so it is never re-sent) and disables the area on `expires_on` (`disabled_at`, plus the `ALERT_TEMP_AREA_EXPIRED` alert). Those three markers make every step once-only; the start and shut-off steps claim the row with a conditional `UPDATE` before patching Dragonite (and release it if the patch fails), so a racing admin edit or Make permanent wins. A row is only marked gone after its area is missing from Dragonite on two consecutive runs (the scheduler keeps the previous run's `missing` ids), and an empty area list skips the run. Nothing re-enables an area after `disabled_at` except `setTemporaryDates` (an admin changing the dates; it only switches the area on if the start is already due).

Follow the subscription-sync pattern — log-and-swallow, started once from `hooks.server.ts` — for any future periodic job that doesn't need live-reconfigurable timing; reach for the self-rescheduling `setTimeout` pattern instead when it does.

### Testing conventions

Tests are colocated (`foo.ts` + `foo.test.ts`), vitest, `environment: 'node'` — no DOM/component testing setup exists, so `.svelte` files are untested directly; only `server/`, `stores` logic extracted into plain functions, and `lib/utils/*` have tests. Mock the DB via the `QueryExecutor` pattern above rather than mocking `mysql2`.
